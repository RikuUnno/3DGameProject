Scene 遷移アルゴリズム（現行実装の動作・説明）

概要
- SceneManager は std::unique_ptr<IScene> をスタックで所有し、現在アクティブなシーンはスタックのトップ。
- シーン遷移は即時実行 API (ChangeScene / PushScene / PopScene) と、フレーム末に反映する保留 API (RequestChange / RequestPush / RequestPop) がある。
- 毎フレームは SceneManager::Update(dt) → SceneManager::Draw() → SceneManager::ProcessPendingChanges() の順で呼ぶ想定。

主要 API の挙動（実装に基づく）
- ChangeScene(std::unique_ptr<IScene> scene)
  - 既存スタックが非空ならトップの `OnDestroy()` を呼び、スタックを clear() してすべて破棄。
  - 渡された scene が存在すれば `Awake()`、`Start()` を呼んでスタックに push_back。

- PushScene(std::unique_ptr<IScene> scene)
  - 既存トップがあれば `OnSuspend()` を呼ぶ（トップを一時停止）。
  - 渡された scene に対して `Awake()`、`Start()` を呼んでスタックに push_back（トップが新しくなる）。

- PopScene()
  - スタックが空なら何もしない。
  - トップに対して `OnDestroy()` を呼び pop_back()。
  - pop 後、スタックが非空なら新トップに `OnResume()` を呼ぶ（復帰処理）。

- RequestChange/RequestPush/RequestPop
  - 保留用のメンバ（m_pendingChange_, m_pendingPush_, m_pendingPop_）に要求を保存。呼び出し時点では遷移は実行しない。

- ProcessPendingChanges()
  - 優先順に保留をチェックし、順次実行する（現在の実装順序: Change -> Pop -> Push）。
  - 実行は単純に各対応関数を呼ぶ:
    - もし m_pendingChange_ なら ChangeScene(std::move(m_pendingChange_))
    - もし m_pendingPop_ なら PopScene(); m_pendingPop_ = false;
    - もし m_pendingPush_ なら PushScene(std::move(m_pendingPush_))

ライフサイクルメソッド呼び出し順（代表例）
- ChangeScene:
  1. oldTop.OnDestroy() （全て）
  2. new.Awake()
  3. new.Start()
- PushScene:
  1. oldTop.OnSuspend()
  2. new.Awake()
  3. new.Start()
- PopScene:
  1. oldTop.OnDestroy()
  2. pop
  3. newTop.OnResume() （存在する場合）

既知の注意点・潜在的問題
- 保留の同時競合
  - 現行 ProcessPendingChanges は Change → Pop → Push を順に実行するが、Change が実行されてもその後の Pop/Push は続けて実行され得る（実装による）。複合遷移が意図しない結果を招く可能性がある。
  - 例: 同フレームに RequestChange と RequestPush があると、Change が行われた後に Push が実行される（結果として Change によってクリアされるべき push が残るケースもあり得る）。
- 安全性
  - Update 中に即時 ChangeScene を呼ぶと、そのフレームの残り処理で参照が壊れる可能性があるため、Update 中は Request* 系を使い、ProcessPendingChanges をフレーム末で呼ぶ設計が推奨。
- ファイル名のタイポ
  - 実装ファイル名が `SceneMnager.cpp`（typo）になっている。将来の混乱防止のため `SceneManager.cpp` にリネーム推奨。

改良提案（実務）
1. 優先ルールの明確化
   - Change がある場合は他の保留をクリアして Change のみ実行（安全性向上）。
   - あるいは「1フレームにつき最大1つの保留遷移のみ実行」ルールを採用。
2. 保留キューの拡張
   - 複数 Push をサポートするキュー構造にする、必要に応じて複数遷移を順番に処理。
3. 遷移予約フラグの原子性（マルチスレッド）
   - 別スレッドから遷移要求する場合は mutex/atomic で要求の同期を行う。
4. テストケース
   - 同時 RequestChange + RequestPush/Pop の振る舞いテストを作成し、期待動作を定義する。

推奨使い方（運用）
- メインループ:
  1. Time::Instance().Update();
  2. SceneManager::Instance().Update(dt);
  3. ClearDrawScreen();
  4. SceneManager::Instance().Draw();
  5. ScreenFlip();
  6. SceneManager::Instance().ProcessPendingChanges();
- Scene 内からの遷移は RequestChange/RequestPush/RequestPop を呼び、ProcessPendingChanges により安全に反映させる。
