生成と所有権ルール（Factory ベース設計メモ）
========================================

目的（要約）
- Factory で生成を一元化しつつ、誰が生成オブジェクトの「所有／管理」を持つかを明確化する。
- 再利用（プール）や遅延生成（Deferred）も扱えるように所有モデルを定める。

基本方針（必須ルール）
1. Factory の責務 = 生成（Create）に集中する。Factory はオブジェクトの長期的管理権を持たない。  
   - Create は `std::unique_ptr<GameObject>` を返し、呼び出し側（通常は Scene / SceneManager）が所有する。  

2. 所有権移転のルールを明文化する（プロジェクト規約）：
   - Factory::Create(...) -> returns unique_ptr -> 呼び出し側が受け取って Scene::AddGameObject(std::move(ptr)) で所有。
   - Scene::AddGameObject は受け取り時に必要なライフサイクル呼び出しを行う（例：Awake() を即時、Start() は次フレーム開始時）。

3. 再利用（Pool）を導入する場合は例外：
   - Pool が内部にオブジェクトを保有し再配布する（取得: Acquire / 返却: Release）。
   - Pool から渡す場合は unique_ptr にカスタムデリータを使い、破棄時に自動でプールへ返却する。  
     → 呼び出し側は「所有しているが実体はプールが管理する」という認識で扱う（借用モデル）。
   - Pool での管理は Factory が行ってもよい（Factory が Pool を内包して Acquire を提供する）。

所有パターン一覧と振る舞い
--------------------------------
A. デフォルト（推奨）
- フロー:
  1. auto obj = Factory::Create("Key", params);
  2. scene->AddGameObject(std::move(obj));  // 所有権は scene に移る
  3. scene が Update/Draw/Destroy を管理
- 所有者: scene（SceneManager 配下）
- メリット: 明瞭、簡単。ガベージレス管理。

B. プール（高頻度オブジェクト）
- フロー:
  1. auto pooledPtr = Factory::AcquireFromPool("Bullet"); // unique_ptr + Deleter
  2. scene->AddGameObject(std::move(pooledPtr));
  3. scene が破棄/返却すると Deleter が Pool::Release() を呼ぶ
- 所有者: 一時的に scene が所有（unique_ptr が保持）。実体メモリは Pool が管理。
- 必須ルール: Acquire で OnAcquire（初期化）、Release で OnRelease（状態クリア）を必ず行う。

C. 遅延（Deferred）生成
- フロー:
  1. Factory::RequestCreate(key, params, callback)
  2. Factory/Loader が非同期にリソースをロード
  3. メインスレッドで callback(std::unique_ptr<GameObject>) が呼ばれ scene で受け取り所有
- 所有者: callback の受取側（通常 scene）
- 留意: メインスレッドで最終生成／初期化を行うこと（DxLib 等の制約）。

ライフサイクル呼び出しのタイミング（仕様化）
--------------------------------
- Awake(): Create() 後、だが Scene に追加される前に呼ぶか、AddGameObject() 内で呼ぶ（設計で統一）  
- Start(): Scene に完全に追加され、次フレーム最初に呼ぶ（Start は一度のみ）  
- Update/FixedUpdate/Draw: Scene のループで呼出し  
- OnDestroy/OnRelease: Scene が削除または Pool に返却するときに呼ぶ

所有モデルの実装パターン（具体）
--------------------------------
- Factory::Create -> returns std::unique_ptr<GameObject>
- Scene::AddGameObject(std::unique_ptr<GameObject> go)
  - 実装:
    - go->Awake(); // or Awake was already called by Factory per project rule
    - components 初期化（必要なら）
    - m_objects.push_back(std::move(go));
- Pool + custom deleter:
  - Deleter = [poolPtr](GameObject* p){ poolPtr->Release(p); }
  - Pool::Acquire returns unique_ptr<GameObject, Deleter>

安全策（必須）
--------------------------------
- 所有権の移転を std::unique_ptr で明示する（raw ポインタだけの受け渡し厳禁）  
- Pool を使う場合はハンドル（index + generation）を検討し、返却済みオブジェクトへの参照・使用を検出する  
- マルチスレッド: レジストリ/プールの操作は mutex 保護。生成自体は可能な限りメインスレッドで行う。  
- 生成エラー: 未登録キーやパース失敗はログ出力 + null 返却 または明確な例外方針を適用する。

設計パターンのまとめ（推奨組合せ）
- Factory（生成統一） + Prototype（Prefab 複製） + Object Pool（高速再利用） + Flyweight（共有リソース）
- Prototype でプレハブを複製し、Pool はそれらの初期化済オブジェクトを再利用する流れが実用的。

チェックリスト（導入時に決めること）
1. Create が戻すオブジェクトは「Awake 済」か「未 Awake」か？（統一）  
2. Start 呼び出しを Scene 側で行うか Factory 側で行うか？（統一）  
3. Pool から返されたオブジェクトの状態初期化（OnAcquire）/クリーン（OnRelease）ルールの定義。  
4. Deferred 生成のコールバック実行スレッドはメインであることを保証する実装。  
5. エラー方針（例外 or null +ログ）。  

短い例（概念コード）
--------------------------------
- Factory 側
  - std::unique_ptr<GameObject> Create(const std::string& key) { return creators_[key](params); }
- Scene 側
  - void AddGameObject(std::unique_ptr<GameObject> obj) {
        obj->Awake(); m_objects.push_back(std::move(obj)); // Start は次フレームで呼ぶ
    }

結論（1行）
- 生成は Factory、長期管理は呼び出し側（Scene/SceneManager）が担い、頻繁に生成破棄するものは Pool で再利用する（Factory と Pool を組合せる設計が最も実用的）。
